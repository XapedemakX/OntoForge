## Ce qui est exact
- YAML : substitutions `_REGION`, `_REPO`, `_SERVICE` valides (préfixe `_`) ; `PROJECT_ID` et `SHORT_SHA` fournis par Cloud Build pour un déclencheur ; image `${_REGION}-docker.pkg.dev/${PROJECT_ID}/${_REPO}/ontoforge:auto-${SHORT_SHA}` cohérente avec le dépôt `ontoforge` (README §2), la région `europe-west1` et le service `ontoforge` (§5, `deploy-demo.ps1`). Trois étapes dans le bon ordre (build, push explicite, `gcloud run services update`) ; `images:` redondant avec le push mais inoffensif (il sert à la provenance). `entrypoint: gcloud` sur l'image `cloud-sdk:slim` correct. `logging: CLOUD_LOGGING_ONLY` obligatoire avec un compte de service dédié : présent. `machineType`/`timeout` identiques à `cloudbuild.yaml`.
- `gcloud run services update … --image` ne modifie que l'image et crée une révision qui hérite de l'ensemble de la configuration du modèle (variables, références de secrets, volume Cloud Storage, limites, compte de service). Même mécanisme que `deploy-demo.ps1`. `env.yaml` n'est donc pas réappliqué (limite bien documentée).
- Syntaxe confirmée par la documentation Google :
  - `gcloud builds connections create github NOM --region=REGION` : correct, affiche le lien d'autorisation de l'application GitHub « Cloud Build » ;
  - `gcloud builds connections describe NOM --region=REGION` : champ `installationState`, `COMPLETE` si installée, sinon le champ donne le lien des étapes restantes ;
  - `gcloud builds repositories create NOM --remote-uri=URL --connection=NOM --region=REGION` : correct (exemple de la doc avec une URL `.git`) ;
  - `gcloud builds triggers create github` : `--repository=projects/*/locations/*/connections/*/repositories/<dépôt>` (2e génération, région explicite obligatoire), `--branch-pattern` (regex, RE2), `--build-config`, `--name`, `--region`, `--service-account=projects/{PROJECT_ID}/serviceAccounts/{ID_OU_EMAIL}`, `--[no-]require-approval` : tout correct tel qu'écrit. `triggers run NOM --branch=… --region=…` correct.
